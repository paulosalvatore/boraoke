**TICKET-82 — the stated black-screen hypothesis was REFUTED, not confirmed.** The queue-update-remounts-the-player theory was disproved empirically first (a rail update keeps the same iframe node). Real cause: the IFrame API's `new YT.Player(el)` **replaces** `el` rather than rendering into it, and the player host lived inside the `nowPlaying ? … : idle` branch — so an emptied queue unmounted that subtree (taking the iframe with it) while `playerRef` kept pointing at a nodeless player (the idle path called `stopVideo()`, never `destroy()`). Refilling the queue mounted a fresh empty host; the effect's "player exists" branch then called `loadVideoById` on a dead player → permanently black embed, refresh-only recovery. **Real trigger: head-of-queue empties, then refills** — an ordinary gap between singers, `/[room]/tv` only. **Second latent defect found in the same pass:** the watchdog's last-resort `recreate` rung reused the same React-owned div, already detached after the first creation, so every "self-heal" attempt built a player into a node no longer in the document — reporting success while the kiosk stayed black, with zero test coverage. Fix is structural: the main row is now mounted for the component's whole life and hidden with `display: none` while idle (React owns only a stable wrapper), a liveness guard drops a player whose iframe left the host, and the player is destroyed on unmount (previously leaked). Negative control at pinned base `93fc367`: the empty-then-refill test goes red there; the other two tests pass at both base and fix, by design. 757 unit tests, zero tsc delta, TICKET-70 rail tests still green at both TV widths. **Recorded at the time as "accepted, not a defect" — that framing was WRONG and is corrected here (see TICKET-89, merged as PR #66, 2026-08-20):** `display: none` on the fullscreen element (or any ancestor) does **not** exit fullscreen — it collapses the element to a 0×0 box with no `fullscreenchange` fired, so the idle transition actually produced a **black fullscreen for the entire gap between singers** (the QR poster rendered but sat unreachable behind an invisible still-fullscreen player), escapable only by a human pressing Esc — worse than "drops out of fullscreen," not "strictly better than the old dead embed." Filed and fixed as **TICKET-89**.

**TICKET-83 — chose sing/vibe before searching, and paginate, under the corrected post-2026-06-01 quota model.** `search.list` = 100 **calls**/day in its own bucket; `videos.list`/`playlistItems.list` = 1 unit against a separate, barely-touched 10,000/day pool (see TICKET-85 below — the board's older "~99 searches/day of 10,000 units" framing is now corrected throughout this document). Effect: common path 2 calls → 1; mode change 1 → 0; "load more" within the first 50 rows → 0 calls; page 3+ refused with no call; worst case per query 2. Key mechanism: `search.list` bills per **call** regardless of `maxResults`, so one 50-row call costs what the old 8-row call cost and covers ~6 client-side pages — `MAX_SEARCH_PAGES = 2` (`lib/youtube-search.ts:112`), nothing prefetched. 18 `Search` i18n keys, identical across all three locales. **The gate caught two real defects the author introduced and would not have found alone:** (1) a **forgeable cache key** — the page marker originally shared a namespace with the lowercased query, and `nextPageToken` is handed to every client, so a crafted query could have planted attacker-chosen videos as "page 2" of a popular search, served to every venue's TV for the cache's 12h TTL; fixed with an **uppercase** marker (`cacheKey()`, `lib/youtube-search.ts:336`) — unforgeable by construction since the query side is always lowercased, first-page key preserved byte-identical; (2) "load more" could pair a new query with a stale cursor, spending a daily search on the wrong query — now structurally unreachable, not merely unlikely. **Deliberate, verified deviation from the original instruction:** the agent did NOT fold sing/vibe into the cache key as directed, because `augmentQuery` already encodes the mode in the query text itself, and a separate cache-key component would split the case where both modes issue an identical search — costing an extra daily search for no benefit. The reviewer independently verified this argument and agreed; the invariant is now documented directly in `cacheKey()`.
